Two things are deliberately not carried across. FFmpeg's encoder lets the three
colour caches survive from one chunk to the next and matches against entries an
earlier frame wrote; this encoder resets them with every packet and only ever
names an entry the same packet has already written, because the two readings of
the format disagree about whether the caches persist and a stream that never
reaches across a chunk reads the same under either. And FFmpeg locates the block
a repeat run copies from by an address computation which, where the run begins at
the first block of a row, names the block at x = width - 4 + (width & 3) of the
row above — the block the row really ends with only when the width leaves nought
or two pixels over a whole number of blocks. Here the source is simply the block
before the run in raster order, which is what both decoders read it as. Nothing
measured reaches the difference: it needs a repeat run to begin exactly at a row
of blocks, which neither encoder's own material produced.
